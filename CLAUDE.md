# Working in this repo

## The one idea

**Never recall this design system's component API from memory. Look it up.**

Every prop this repo's components actually have is either read straight from
source by a command, or written to a generated file straight from that same
source. Neither can drift from the code, because neither is hand-maintained.
Guessing a prop name is never faster than the fifteen seconds it takes to
look it up, and a wrong guess (`<Button kind="primary">` instead of
`variant`) is exactly the failure mode this file exists to prevent.

See [agent-workflow.md](agent-workflow.md) for the general version of this;
this file is that workflow applied to this specific repo.

## Look it up

```sh
npm run ui -- list                 # every component, one line each
npm run ui -- props <name>         # props, types, defaults — read from source
npm run ui -- props <name> --example  # + a real usage snippet from apps/
npm run ui -- tokens [filter]      # --ds-* custom properties, optionally filtered
npm run ui -- pages                # existing page shells (find the precedent)
```

Add `--dense` to any of the above for compact output worth pasting into a
chat window. `.claude/ui-context.md` is the same information as one static
file — generated by `npm run ui:sync`, which `npm run build` also runs as
its last step, so it's never more than one build behind the source. Prefer
the live commands when investigating one component; read the file when you
want the whole surface at once.

**Component names are `kebab-case` and match the registry exactly**
(`button`, `state-layer`, `text-field`) — check `npm run ui -- list` before
typing one from memory, including the ones that don't exist yet
(`card`, `table`, `dialog` is real but unbuilt — see below).

## Pre-write ritual

Before writing any UI code in `apps/*` or adding a component under `packages/`:

1. **Find the precedent.** `npm run ui -- pages` — is there a page in this
   repo with a similar shell? Right now there's exactly one
   (`apps/playground/src/app.tsx`, shell: `header → section×3`, no sidebar).
   Open it before adding a second one.
2. **Study the frame.** Read that page's layout shell only — ignore its
   content. What are the regions, and how wide is each one?
3. **Read the props.** `npm run ui -- props <name>` for every component the
   new code touches, no exceptions for "obvious" ones. `Button` is small and
   still has a non-default prop (`iconOnly`, `loading` with the aria-disabled
   pattern below) that's easy to invent wrong.

If the command says *"There is nothing to look up — don't invent props for
this one"* (`dialog`, `text-field` today), that component doesn't exist yet.
Say so and stop — don't write a plausible-looking `<Dialog>` API.

## Adding a new component — gated build order

This is about extending the design system itself, not consuming it from
`apps/*` — see [STRUCTURE.md](STRUCTURE.md#how-a-component-becomes-real) for
the full walkthrough. The short version: **primitives → approved → semantics
(token mapping, approved state by state) → approved → component (CSS/React)**.
Each arrow is a stop-and-check, not a formality — nothing in the tooling
blocks skipping ahead, so don't skip ahead. Concretely: don't write
`packages/css/src/<name>.css` until the primitive's behavior/API is approved
*and* every state's token mapping is approved individually; don't guess at a
mapping to keep moving.

## Frame-first layout

Decide the shell before the content: pick header / sidebar / centered /
full-width, name the regions, budget them, *then* fill.

| Content type | Container |
|---|---|
| Dense, scannable rows | `<table>`/list, edge-to-edge, divided — see `.pg-table` in `apps/playground` | 
| Widgets, galleries, settings groups | Card |
| Everything else | Neither — plain `<section>` |

**There is no `Card` component yet.** It isn't in the registry
(`npm run ui -- list` won't show one), so don't hand-roll a `<div className="card">`
as a stand-in — that's exactly the kind of ungoverned pattern the registry
exists to prevent. Use a plain `<section>` and flag the gap instead.

## Token discipline

Every value comes from `@ds/tokens`, exposed as `--ds-<path>` custom
properties (`npm run ui -- tokens` for the full list). Never a bare hex or
pixel value in component CSS or inline styles.

- **Semantic first.** Reach for `--ds-color-accent-role-bg` before
  `--ds-color-accent-600` — the `-role-*` tokens are the ones that survive a
  theme or brand change; the numbered scale under them is raw material.
- **New token needed → use the `design-tokens` skill**, not an ad hoc edit
  to `packages/tokens/src/semantics/*.json`. It's the Gate 1/2/3 interview that
  gets a new primitive or semantic token proposed, described (Purpose / Use
  when / Don't use for / Pairs with), and approved before it's written —
  see [STRUCTURE.md](STRUCTURE.md#the-design-tokens-skill-and-this-repos-actual-token-pipeline)
  for how it maps onto this repo's actual JSON pipeline.
- **Compose the state layer, don't reinvent it.** Interactive components get
  hover/press feedback by adding the `ds-state-layer` class alongside their
  own (see `.ds-button` in `packages/react/src/button.tsx`), not by writing
  a new `:hover` background rule.
- **`aria-disabled`, not `disabled`.** Disabled controls in this system stay
  focusable and screen-reader-discoverable; activation is blocked in the
  primitive (`packages/primitives/src/button.ts`), not by the native
  attribute. Follow this pattern for any new interactive primitive.
- **CSS load order is manual, not cascade-layered yet.** `packages/css/build.mjs`
  concatenates files via an explicit `ORDER` array (state-layer → spinner →
  button today) — there's no `@layer` boundary protecting overrides. Adding a
  component whose CSS must come before another's means adding it to `ORDER`,
  not relying on file listing order.

## Anti-patterns

| Don't | Instead |
|---|---|
| Invent a prop | `npm run ui -- props <name>` first |
| Hardcode a color or pixel value | The matching `--ds-*` token |
| `disabled` attribute on a new interactive primitive | `aria-disabled` + a click guard, like `getButtonProps` |
| A new `:hover`/`:active` rule for feedback | Compose `.ds-state-layer` |
| A `<div className="card">` wrapper | Plain `<section>` — there's no Card yet, don't invent one |
| Wrap a component in a div just for spacing | A `--ds-space-*` token on the component or its parent |
| Add new component CSS and assume load order | Add the file to `ORDER` in `packages/css/build.mjs` |
| Write CSS/React for a new component before its primitive and token mapping are approved | Follow the gated order above — primitives approved, then semantics approved state by state, then component |

## Knowledge check

Before writing code that touches `@ds/react`, you should be able to answer
these without looking — if you can't, run the lookup commands above first:

1. What is the exact import path for `Spinner`'s CSS if a consumer isn't
   using React?
2. What prop makes `Button` show a spinner and refuse clicks while staying
   focusable?
3. Is `Dialog` implemented? What does `npm run ui -- props dialog` tell you
   to do about it?

(Answers are in `.claude/ui-context.md` and `packages/react/src/button.tsx`
— the point isn't memorizing them, it's noticing when you'd have to guess.)

## Maintenance loop

| Trigger | Action |
|---|---|
| Component added, renamed, or its props changed | `npm run ui:sync` (or just `npm run build`, which runs it last) |
| A registry manifest changes (`registry/components/*.json`) | Same — `npm run build` |
| You give the same correction twice in one session | It belongs in this file, not a chat message |
